# ADR-001: Keep the Unity OpenXR: Meta route for all MR features

Date: 2026-09-25 · Status: accepted

## Context
design.md §5.1 chose AR Foundation via the Unity OpenXR: Meta feature group for passthrough, scene mesh, anchors,
occlusion and passthrough camera images, with the Meta XR Core SDK + MRUK as the fallback for any feature that proved
unreliable. Spike #3 built the smallest scene that exercises all five (`Assets/_Project/Scenes/Spike/PlatformSpike.unity`,
generated by `Fieldmate/Spike/Build Platform Spike Scene`) and ran it on a Quest 3 (Horizon OS, Unity 6000.4.9f1,
OpenXR 1.18.0, AR Foundation 6.6.2, Unity OpenXR: Meta 2.6.1).

| Feature | Result on Quest 3 | Notes |
|---|---|---|
| Passthrough | works | `ARCameraManager` + camera background alpha 0; URP HDR off, no post-processing, terrain holes off, intermediate texture Auto |
| Scene mesh | works | `ARMeshManager` (child of XR Origin) receives the Space Setup room mesh as **one** chunk; empty until Space Setup has been run |
| Persisted anchor | works | `TryAddAnchorAsync` → `TrySaveAnchorAsync`; after an app restart `TryLoadAnchorAsync` restores it in place (`UnqualifiedSuccess`) |
| Depth occlusion | works | `AROcclusionManager` + `ARShaderOcclusion` (hard); materials need an occlusion-aware shader (`Fieldmate/Spike/OccludedUnlit`) |
| Camera frame | works | `ARCameraManager.TryAcquireLatestCpuImage` → RGBA32 `Texture2D`, 1280×960, intrinsics f≈863.8 px, c≈(639, 481) |

Findings the rest of the project has to respect:
- **Runtime permissions are the app's job.** The package adds `USE_SCENE` and `HEADSET_CAMERA` to the manifest but never
  requests them. Mesh and occlusion stay disabled until `USE_SCENE` is granted; the camera manager stays disabled until
  `HEADSET_CAMERA` is answered. Restarting an already-running camera manager after a late grant stopped passthrough on
  device (black view), so the camera starts once, after the answer (`Fieldmate.XR.QuestPermissions`).
- **No camera extrinsics.** Nothing in this route exposes the passthrough camera's pose. `CapturedFrame.HeadPose` is the
  head pose at acquisition, which is an approximation. PixelToRay (M2 Vision) must add a fixed head→left-camera offset
  (measure or take from Meta's published values) and accept a small error, or the vision step leans on gaze + twin
  candidates (design.md §5.5 step 5), which it already does.
- **Timestamps are nanoseconds.** `XRCpuImage.timestamp` from this provider is in ns (e.g. 7224595716000), not seconds.
- **Image orientation.** AR Foundation's sample conversion (`Transformation.MirrorY`) gave a 180°-rotated image; use
  `MirrorX` (verified on device).
- **Meta anchors cannot be listed.** `TryGetSavedAnchorIdsAsync` is unsupported; the app stores saved ids itself
  (`Fieldmate.XR.AnchorIdCodec`, PlayerPrefs in the spike).
- **Hand pinch input flickers.** `MetaAimHand` `indexPressed` re-triggers several times per pinch; interactions need a
  debounce/hysteresis (the spike uses a 1 s cooldown).
- **Space Setup is a prerequisite.** Without it the mesh is empty and pointer raycasts fall through the floor; the app
  should detect this and send the user to Space Setup.

## Decision
Keep the Unity OpenXR: Meta route for all five features. No feature moves to the Meta XR Core SDK / MRUK.

## Consequences
- One API family (AR Foundation) for all MR features; `Fieldmate.Unity` depends only on AR Foundation, XR Core Utils and
  the Input System, not on a vendor SDK.
- Permission handling, the Space Setup check, input debouncing and the camera pose approximation are ours to build and
  test (tracked in the M1/M2 issues).
- Occlusion needs our own shaders (or shader-graph nodes) for every occludable material; budget this in the perf pass.
- Revisit if PixelToRay accuracy without extrinsics misses the T2 target (≥ 80% correct labels): the Meta SDK's
  `PassthroughCameraAccess` exposes camera poses.
